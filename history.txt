● I'd suggest building a single dashboard view with a search/query bar at the top, and structured result cards below — rather than  
  separate tabs per journey. The use-cases all start with a natural language question and return structured graph data, so one      
  unified input that routes to the right query pattern (service lookup, role tooling, spend chain, escalation) keeps the UX simple  
  and matches the "Who Knows What?" bot concept. We can use useTriples() for the simple lookups (service ownership, role tooling)
  and SPARQL for the multi-hop ones (approval chains with spend thresholds).                                                        
                                                                                                                                    
  The main tradeoff: a unified search is more natural but means we need query classification logic up front. The alternative — one  
  tab per journey — is easier to build but feels more like an admin tool than a conversational assistant.                           
                                                                                                                                    
  I'd build it in this order:
  1. Shell: replace the template tabs with the new layout (search bar + results area)
  2. Service ownership card: simplest query, proves the data path end-to-end                                                        
  3. Role-based tooling card: similar pattern, different query              
  4. Spend approval chain: the most complex rendering (tiered steps)                                                                
  5. Escalation path: reuses patterns from 2 + 4                                                                                    
                                                                                                                                    
  Want me to go with this, or would you prefer the tabbed approach?                                                                 

❯ You know there's a graph embeddings query available, btw?  That's useful for searching.   Plain text -> embeddings -> graph       
  embeddings.                                                                                                                       
                                                                                                                                    
● Good point — that changes the approach nicely. Instead of building query classification logic, we can use useEmbeddings() to      
  vectorize the user's plain text input, then useGraphEmbeddings() to find the nearest entities in the graph. That gives us a
  natural entry point: user types anything, we find the relevant entities (a service, a role, a team), then follow the graph        
  relationships from there with useTriples() to build the result cards.
                                                                                                                                    
  So the flow becomes: free text → embeddings → nearest graph entities → triple traversal → structured card.                        
   
  That eliminates the need to parse or classify the query — the vector search handles the intent mapping implicitly. We'd still use 
  SPARQL for the spend approval chain (needs threshold filtering and ordering), but everything else can be triple lookups radiating
  out from the matched entity.                                                                                                      
                  
  Same build order, just with embedding search as the universal entry point instead of per-journey routing. Want me to start?
